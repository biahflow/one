# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Portal Labs — a multi-tenant client portal where customers track AI project progress, results, and decisions, with a context-aware assistant that answers **only** with evidence from the project (citations, never invention). Product docs are PT-BR; code, API, and DB identifiers are English.

## Engineering OS

Read [`AGENTS.md`](AGENTS.md) and [`docs/project-context.md`](docs/project-context.md) before
planning or changing work. `ROADMAP.md` is the work-discovery index; an FDD is the detailed
Feature Contract and lifecycle authority when one exists. ADRs record decisions and RFCs retain
context rather than implementation status. The prospective plan/task/evidence layout is documented
in [`docs/features/README.md`](docs/features/README.md); human approval remains required at every
applicable gate.

The repo is a monorepo, and Fase 1 (identity, roles, RLS) is complete on both halves. **The API** validates the OIDC access token, authorizes from the `membership` and enforces Row-Level Security (ADR 0010) — every client endpoint requires `Authorization: Bearer` and answers 404, never 403, on a denial. **The web layer** is a real OIDC client: Auth.js v5 does the code exchange server-side, `proxy.ts` closes everything but `/login`, and `app/page.tsx` renders from the API. There is no fallback to fabricated data any more — 401 goes to `/login`, 404 says "no project assigned", a network failure is an error panel. Fase 1 is now closed end to end: an internal admin invites someone at `/admin`, the person gets an e-mail from Keycloak, sets a password and lands on their project. **Fase 2 is closed too**: a change in Biahflow becomes a notification in the bell and a digest e-mail, produced by the sync itself (ADR 0012). **Fase 3 closed the results pipeline** (ADR 0013): agents publish idempotent events through the one key-authenticated route, financial assumptions carry an effective range, and ROI is computed at read time from the assumption in force *on the day of the event* — so the last three demo cards and the fabricated ROI fallback are gone from the client's screen. **Fase 4 gave the assistant eyes** (ADR 0014): an internal member uploads a file at `/admin/conhecimento`, the worker turns it into page-anchored chunks with embeddings in pgvector, and the chat now cites "Documento: Contrato — página 3" instead of declaring a gap. **And it gave the conversation a memory** (ADR 0015): the turn no longer lives in a `useState` — question, answer, confidence and the citations *as they were shown* survive the reload, and a thumb records whether the answer helped. **Fase 4 is now closed** (ADR 0016): an internal admin connects one Google Drive folder per project with a read-only consent, and its content flows into the same index without anyone re-uploading a file — the folder boundary is checked twice, a shortcut is never followed, and a failure at Google pauses the folder instead of deleting the index. **Fase 5 abriu pelo ciclo de vida do documento** (ADR 0017): o arquivo é varrido antes de qualquer parser abri-lo, a citação virou link que abre a fonte por URL assinada de vida curta, e o dado passou a ter prazo — com o apagamento por organização executado pelo worker, nunca por uma rota HTTP. **E seguiu pela telemetria** (ADR 0018), que não implementou uma promessa adiada e sim três que os documentos já davam como cumpridas: um `trace_id` que o runbook de incidente mandava preservar e não existia, campos de `extra` que o runbook de eventos mandava ler e que o `logging` sem formatter descartava, e um "A falha foi registrada" que a tela de erro dizia sem nada registrar. **A quarta fatia publicou o contrato** (ADR 0020): o `api-contracts.md` prometia que o OpenAPI publicava tudo automaticamente enquanto as dezesseis rotas de cliente devolviam `dict` cru — e documentava camelCase para uma API snake_case. Agora o esquema é artefato versionado com gate de deriva, o "404, nunca 403" é propriedade verificada de toda rota, e o verde do CI parou de afirmar o que não provava: as asserções de restore que pulavam em silêncio a cada push falham, e o e2e pode reprovar. **A quinta fatia foi atrás do que a IA promete** (ADR 0021), e foram quatro promessas de uma vez: o `prompt-policy.md` dizia "prompts são versionados" e o que existia era uma setting que ninguém lia; as catorze evals de injeção rodavam no respondedor offline, um casador que não tem como obedecer a uma instrução; o `threat-model.md` prometia limite de taxa no chat e não havia nenhum, embora cada lacuna grave uma pendência; e o runbook do provedor mandava procurar um evento que o código nunca emitia. Agora a versão do prompt mora ao lado do texto com registro de digests como portão, o turno guardado sabe qual prompt e qual modelo o produziu, as evals rodam contra o `AnthropicResponder` real com um Claude hostil — metade delas afirmando sobre o **pedido enviado**, que é a única forma de provar que segredo e texto de outro projeto não saem do processo —, e o chat tem janela por pessoa em tabela própria. De quebra, os dois defeitos que só apareceram porque alguém finalmente executou aquele código: um `max_tokens` que truncava a resposta e virava fallback silencioso, e o `answerFor()` da tela, que devolvia data, decisão e **citação inventadas** ao cliente cuja chamada falhou — com um teste que exigia sua existência. A frase acima sobre não haver mais fallback para dado fabricado só passou a ser verdade aí. **A sexta fatia** (ADR 0022) repetiu o padrão pela sexta vez — só que desta vez a promessa não cumprida era a *causa* do item estar aberto: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` e `CHAT_RATE_LIMIT` existiam no `.env.example` desde a Fase 3 e **nenhum compose as passava ao contêiner**, de modo que o `AnthropicResponder` da ADR 0021 nunca havia rodado na pilha de pé e uma medição de carga mediria o Postgres. Agora a homologação existe como código com dois portões independentes contra o segredo do exemplo, a conta de IA tem razão de tokens e teto por organização com o dinheiro nascendo na leitura, e o harness de carga recusa rodar sem orçamento declarado e diz no próprio relatório o que mediu. **E a sétima fechou a Fase 5** (ADR 0023), com o padrão pela sétima vez e desta vez a instrução escrita levando ao lugar errado: o `security.md` mandava ir até o `next@16.2.11`, que fecha os nove avisos do `next` e repina `postcss` e `sharp` **vulneráveis** — só a 16.3.0 zera —, e tranquilizava com uma frase invertida, porque Turbopack **é** o bundler deste repositório (o que não se aplica é a outra pré-condição, e `config.i18n` não existe aqui). O `dependency-review` do CI parecia varredura e olha só o *diff* de um PR, então o lockfile passava verde a cada push; e o lado que nenhum documento mandava olhar, o Python, tinha **dezesseis** avisos contra os catorze do lado nomeado — seis no `python-multipart`, que sustenta a única rota multipart do produto, e sete no `starlette`, que é a camada HTTP inteira. De quebra, dois defeitos que só apareceram por executar aquilo: subir o FastAPI conserta o Starlette só em instalação limpa (a faixa nova é `>=` sem teto), e o FastAPI 0.141 passou a **ecoar o corpo da requisição** em todo 422 — sendo que `DriveCallbackIn` carrega o authorization code do Google, de modo que a fatia teria *introduzido* o vazamento do segredo que a ADR 0016 sela. Agora os dois ecossistemas têm portão que reprova a cada push, sem limiar de severidade, e aceitar um risco é escrever linha com motivo e prazo que **vence**. **E a Fase 6 abriu pela busca** (ADR 0024), que repete o padrão com uma diferença que pesa: as promessas anteriores estavam em documentos, e esta estava **na tela do cliente** — a lupa do topbar abria um `<input>` sem `onChange`, sem handler e sem resultado, embaixo da frase "Comece a digitar para buscar no contexto do projeto". Aquela ADR chamou a lupa de "o último resto de casca de demonstração no produto" e **errou**: havia mais onze botões inertes na mesma tela, que a **ADR 0026** ligou (dois) ou apagou (nove) — e cuja sobrevivência tem uma causa que virou portão, porque toda guarda deste repositório era sobre *dado* e um `<button>` sem `onClick` renderiza HTML idêntico a um que funciona. `inertButtons()` em `tests/rendered-html.test.mjs` é a primeira asserção que olha a **forma do controle** e não um valor. A busca fechou junto o critério de aceite da Fase 1, que exigia falha de acesso cruzado "na API, no banco **e na busca**" e trazia em itálico a ressalva de que a busca chegaria com o RAG da Fase 4: a Fase 4 veio, o RAG chegou e alimentou o *chat*, que é outra coisa. **E a quarta repetição do padrão foi atrás de uma guarda de CI** (ADR 0033) — o mecanismo que existe para as promessas não serem quebradas. A guarda da ADR 0029 dizia que "o contrato tem de ser consumido, não só casado" e que sua allowlist estava "vazia, e a meta é que continue"; ela era um `for` sobre **oito nomes escritos à mão** lendo **um arquivo**, num contrato com **56 esquemas de resposta** — a allowlist seguia vazia porque nada a consultava, que é a forma do `dependency-review` da ADR 0023. Generalizada, nasceu vermelha com catorze campos e uma rota, e os três que importam não eram campo faltando e sim a tela afirmando o que não é: a linha "Fórmula do ROI" imprimia um **literal** que nem casava com a fórmula que a API devolve, no bloco "Como calculamos" que a Fase 3 abriu para o cliente conferir a conta; `feedback_comment` **não tinha escritor**, e `/admin/assistente` mostrava um painel intitulado "O que os clientes disseram" sobre um campo sempre nulo; e `last_sync_stats` deixava uma sincronização truncada indistinguível de uma completa. A decisão que carrega o resto foi **medida**: a primeira versão da guarda usava um corpus único sobre `app/`, ficou verde, e não reprovava ao neutralizar `.priority` — nasceria verde em cima do defeito exato que a ADR 0029 existe para pegar. **E a quinta repetição foi atrás da telemetria** (ADR 0034), com um argumento diferente: a promessa já tinha sido consertada à mão e voltou a quebrar. A ADR 0028 achou o `alerts.md` citando `drive.rejected`, evento que o código nunca emitiu, corrigiu a linha e não deixou guarda — em dois dias o arquivo divergiu de novo pelo outro lado, com doze eventos emitidos que nenhum runbook conhecia. O runbook mandava vigiar `scan_state=skipped` para descobrir que o antivírus caiu, o que é **impossível** (com `CLAMAV_HOST` configurado o scanner responde `clean`, `infected` ou `error`, nunca `skipped`), e `error` não tinha linha em lugar nenhum; dez sítios punham a mensagem **já interpolada** no campo `event`, produzindo um valor novo por ocorrência — e um runbook mandava procurar um deles por substring, única instrução do repositório que não se cumpria por `event`; e "anomalias de autorização" era indicador sem emissor, com `access.py` tendo quatro caminhos de negação e zero logs. Agora a negação emite `authz.denied` com `reason` e `subject_prefix`, **sem mudar o 404 opaco** que o chamador recebe, e a guarda é bidirecional (evento emitido tem runbook, evento de runbook é emitido) ignorando as notas históricas — senão cobraria que o repositório apagasse o registro do próprio erro. De quebra, a guarda achou o que o levantamento manual não viu: `http.failed` e `health.broker_unavailable`, este último irmão exato de um evento que já tinha limiar. **E a sexta repetição foi atrás do mecanismo inteiro** (ADR 0035): as guardas que carregam as regras inegociáveis eram, elas próprias, listas digitadas — o defeito da ADR 0033 sobrevivendo em quatro lugares, três deles a única prova executável de uma regra do `AGENTS.md`. A **regra 2** ("nunca envie segredos ao modelo") era provada por seis sentinelas fixas contra dezesseis campos de segredo, e os quatro que mais importam escondem a credencial **dentro do valor** — as `database_*_url` são DSN completo e não casam `_SECRET_HINTS`, porque aquele casador pergunta pelo *nome*, que no log é a chave do `extra` e ali está certo; ficavam de fora a chave **anterior** da rotação do Drive e a senha do `portal_admin`, e medindo com um vazamento injetado a guarda nova reprova enquanto a antiga passa verde. A **regra 6** — caso negativo de permissão — não tinha portão nenhum: 30 funções à mão contra 46 pares rota+método publicados, e `GET`/`PUT .../ai-quota`, que definem o teto de gasto de IA de uma organização e têm tela desde a ADR 0027, **não tinham teste de espécie alguma**. A guarda nasceu vermelha com cinco pares, e o mais caro não era o teto: `GET /projects/{id}/results` é a única rota de cliente que recebe id de projeto no caminho — o caso literal da regra 1 — e ninguém a exercitava. O predicado sai do artefato publicado (**quem promete 404 prova o 404**), o que dispensa allowlist, e o elo foi medido como na ADR 0033: com a ligação frouxa, `POST /chat` aparecia coberto por um 404 que era de outra rota. Mais o `pytest.skip` cru que escapou do `skip_unless_ci` justo sobre "restaurar bytes corrompidos é pior que falhar", e a guarda de eventos que só via metade do repositório — o BFF emite quatro eventos e nenhum tinha runbook, com um `elsewhere` dentro da própria guarda descrevendo o ponto cego em vez de fechá-lo. De quebra, o que fecha o círculo: **a numeração que todo mundo cita não existia** — cinco princípios no `AGENTS.md` contra seis no `CLAUDE.md`, que promovia uma convenção e um item de checklist a princípio e descartava o princípio 5; era a numeração da cópia que circulava, com seis lugares citando uma "regra 6" inexistente. A **regra 4** fica declaradamente sem guarda, e é a única. **E a nona repetição foi atrás de um documento de três linhas** (ADR 0038): o `context-contract.md` prometia desde a Fase 3 que "toda citação aponta para fonte, localização e **data**", e nenhuma citação tinha data — enquanto `Document.source_updated_at`, `indexed_at` e o `PendingItem.created_at` carimbado com o `opened_at` do Biahflow já estavam no banco sem consumidor. O que dá peso é o turno guardado: o `drive_sync` reindexa a **mesma linha** quando o arquivo muda e `conversation_message.citations` congela o rótulo, de modo que a citação clicável da ADR 0017 — criada *para o cliente conferir a fonte* — abre meses depois uma versão diferente daquela em que a resposta se apoiou, com rótulo idêntico. A medição também impôs um **limite** à promessa: marco e status não ganham data, porque a linha do marco é apagada e recriada a cada sync e o `created_at` dela é a hora da cópia; carimbá-la seria a falsa precisão que `results.py` recusa, e o documento foi corrigido para dizer isso. De quebra, **dois portões nasceram cegos e foram medidos**: o `template_sha256` do registro de prompts não mudou ao acrescentar data à linha da evidência, porque a sentinela do digest não tinha data — a cobertura de um portão é a dos ramos que a amostra percorre —, e o campo chamado `date` passava verde na guarda de consumo **sem consumidor nenhum**, porque ela casa nome por substring e `date` aparece em `new Date` e `due_date`: é o `.priority` da ADR 0033 outra vez, e renomear para `dated_at` foi o que tornou o elo verificável. **E a Fase 7 abriu pelo funil** (ADR 0039), primeiro item construído de uma fase que outra sessão propôs no mesmo dia: o produto sabia se um projeto está no prazo e **não sabia se o cliente engaja**, com um projeto verde cujo cliente parou de logar sendo churn silencioso. O recorte veio da RFC 001 e é o inverso do costume — **escritor primeiro, leitor depois**, porque a ADR 0033 achou um painel publicado sobre campo que nunca teve escritor: `onboarding_step` carimba seis degraus e **nenhuma tela os mostra ainda**. O carimbo é imutável (`UniqueConstraint` + `ON CONFLICT DO NOTHING`, e **nenhum papel tem `UPDATE`**), `portal_app` fica **sem policy nenhuma** — um caminho de requisição capaz de escrever o próprio degrau é um caminho capaz de falsear o próprio engajamento —, e quem escreve é `onboarding.stamp` em transação própria sob `portal_system`, no precedente do `chat_limit.consume`. O login é carimbado no **dashboard** e não em `identity.resolve_user`, porque lá ainda não há organização resolvida (o próprio módulo diz isso ao explicar por que não grava `audit_log`), e o degrau fica melhor definido: aceitar o convite passa a significar entrar e ver o projeto. `artifact_accepted` ficou **fora do enum** por não ter produtor — o snapshot não carrega artefato. O apagamento por decisão precisou de exclusão **escrita à mão**, e isso corrigiu um docstring: o funil é escopado por organização e não vem no CASCADE do projeto, então a `membership` deixou de ser a única exceção. De quebra, o defeito que só apareceu ao executar: `bool(rowcount)` **não** diz se a linha nasceu — `ON CONFLICT DO NOTHING` devolve `-1` nos dois casos e `bool(-1)` é `True`, de modo que todo carimbo se dizia "primeira vez" e o evento sairia a cada download; a resposta confiável é `RETURNING`. **E o passo 3 deu leitor ao funil** (ADR 0040): `/admin/funil` lista os clientes travados por gravidade, separando "travou no cliente" de "travou em nós" em **dois painéis com três contadores e nenhum total** — a exigência da FDD 020 virou estrutura do componente, não convenção. O degrau atual é o **mais baixo em aberto** e não o mais alto alcançado, porque o degrau do Biahflow chega retroativo; a rota **autoriza sob `portal_admin` e computa sob `portal_system`**, porque `pending_item` não tem policy `TO portal_admin` e o `EXISTS` de "há pendência aberta?" responderia "não" para toda organização, rotulando todo cliente do produto como *travou em nós* — o desenho que a ADR 0039 escolheu de propósito para `portal_app`, achado pelo avesso; e o alerta toca **uma vez** por organização e degrau porque a memória dele já existia, o `dedupe_key` da notificação, o que dispensou a tabela que a ausência de `UPDATE` no funil tornaria inevitável. `NotificationKind.onboarding_stuck` é o primeiro aviso só do time e o primeiro uso do `_INTERNAL_ONLY` que a ADR 0012 definiu e nunca usou — com guarda nova de completude do `AUDIENCE`, porque o `.get(kind, _CLIENT_ONLY)` de `recipients` faz o esquecimento **contar ao cliente** que ele está sendo medido. De quebra, o defeito que quase fez a medição nascer cega: no primeiro dia da instrumentação *toda* organização é anterior a ela, e a tela nasceria mandando ligar para todo cliente do produto para dizer que ele nunca entrou — a saída foi `user.external_subject`, a evidência que a RFC 001 apontava e que é a única corroboração de degrau fora do funil. **E o sétimo degrau fechou o critério que a FDD 020 deixou "adiado, e não esquecido"** (ADR 0041): `artifact_accepted` estava fora do enum com a condição escrita — *"ele entra quando o outro lado o afirmar"* —, e o outro lado tinha o dado inteiro desde a FDD 016 dele (`Artifact` com `sent → accepted`, `decided_at` no `save()`, o e-sign fechando o contrato sozinho) sem que ele atravessasse: `build_snapshot` não levava artefato e `signals.py` não tinha receiver, a forma da ADR 0037 um degrau antes. Agora atravessa **só a data** — nem `kind`, nem `title`, nem `content` —, com a linha "nenhum dado comercial é exposto" de lá **qualificada em emenda** na ADR 0003 daquele repositório em vez de contornada. **O que a fatia destrava não é um item de lista, é a régua:** o `_anchor` nunca teve o *ganho* e contava do convite, de modo que a demora entre fechar o contrato e convidar a pessoa — que é **nossa** — encurtava o número em vez de aparecer nele. O degrau entra **primeiro** na escada, é sempre `Blame.us` (o portal não hospeda aquela aprovação nem tem como coletá-la) e ganhou a corroboração do login desta vez **prevista**: projeto vivo significa negócio fechado, senão toda organização anterior à fatia apareceria mandando cobrar contrato assinado há meses; na prática ele nunca é o degrau travado, e isso é a resposta certa, porque "não registraram o artefato" é higiene de cadastro e não desengajamento. De quebra, um defeito **da ADR 0039** que só apareceu ao construir o sétimo: `sync_snapshot` **cria** a organização e chamava um `stamp` de sessão própria, então no primeiro snapshot de um cliente novo a chave estrangeira barrava o `INSERT`, o carimbo se perdia em silêncio e saía `onboarding.stamp_failed` — que o `alerts.md` diagnostica como indisponibilidade do banco. Valia para o entregável desde sempre (medido), era raro lá e é o caso central aqui; `stamp_within` carimba dentro da transação que já é do sistema, com `SAVEPOINT`, porque um `IntegrityError` deixa a transação abortada e engolir a exceção sem ele trocaria um degrau perdido por um **snapshot** perdido. **E as duas fatias seguintes foram o teto e o canal** (ADR 0042 e 0043). O teto de frequência de contato saiu em **fatia própria**, contra o combinado de sair junto da FDD 022: aquela FDD está bloqueada por uma condição que não é código e a FDD 021 não está, então manter o acordo entregaria o canal **sem teto** — justamente o que as duas FDDs chamam de "o mais fácil de queimar" — ou prenderia o canal atrás de condição alheia. É **razão e não contador**, contra o precedente do `chat_rate_window` e pelo argumento que aquele módulo já tinha escrito: um contador subconta sob concorrência, o que no chat deixa passar uma pergunta a mais e aqui deixa passar **uma mensagem a mais para uma pessoa**. O preço está pago em vez de contornado — tenant, policy, poda e a **terceira** exclusão à mão no apagamento —, e a policy **nega por escrito** (`USING (false)`) em vez de negar por omissão como as três tabelas anteriores sem leitor, porque a omissão reprovaria o meta-teste de RLS e a saída fácil (conceder `SELECT` ao admin "para a tela que virá") é o defeito da ADR 0033 escrito ao contrário. De quebra, o que a fatia mediu e a FDD 022 não sabia: o teto global **não** satisfaz sozinho o critério (2) de lá, porque "segundo evento na mesma semana" é afirmação sobre a *espécie* e não sobre o volume. **E o canal de WhatsApp descobriu que metade dele não era o canal** (ADR 0043): o critério (4) da FDD 021 exige que o link caia "na coisa exata, nunca na home", e não havia link nem URL que o suportasse — `Notification.link` existe desde a Fase 2 e o sino o renderiza como `<a>`, e as dez ramificações do `diff` **nunca o preencheram**; é a ADR 0033 na direção que ninguém tinha olhado, porque lá era um painel sobre campo sem escritor e aqui um **controle** sobre campo sem escritor, que a guarda de consumo não pega (ela pergunta se há consumidor, e há — faltava produtor). A navegação por abas era estado de React sem URL que a alcançasse, então nem havia o que escrever: `tabs.py` nasceu pela razão do `textfold.py` (o mesmo literal em três arquivos, e a divergência não deixa nada vermelho), a aba virou `?tab=`, o `LINK_TAB` deu escritor ao campo e **o sino ganhou links de carona**. A mensagem não tem campo livre — dois parâmetros, o fato e o link, e o `detail` não entra —, o consentimento é conferido **no envio** (é o que faz a revogação alcançar a fila), nasce desligado ao contrário do e-mail, e há **duas** colunas de carimbo porque num carimbo só o SMTP fora do ar cancelaria o WhatsApp. Três guardas cobraram durante a construção e as três estavam certas: `phone_hint` reprovou por ter nome de segredo (a resposta foi a allowlist, como o `key_prefix` — renomear passaria pela guarda sem mudar o dado), a guarda de consumo mostrou que a tela **recalculava** o `phone_hint` em vez de ler o do servidor, e a de allowlist obsoleta cobrou a linha que dizia que aquele campo era "eco que a tela já sabe". See `ROADMAP.md` for what is next.

## Architecture

Three deployables (`docs/architecture.md`):

```
Browser → Next.js BFF → FastAPI → PostgreSQL + pgvector
                         ├→ Redis/Celery → Drive, email, indexing
                         └→ MinIO/S3 → documents & transcripts
```

- **`app/` (+ `auth.ts`, `proxy.ts` at the root)** — the web frontend: stock **Next.js 16** (App Router, React 19 RSC) served by `next start` on Node, containerized like every other service (ADR 0009). `auth.ts` configures Auth.js v5 with the confidential Keycloak client; `proxy.ts` (Next 16's name for the middleware) is the session gate — a redirect for pages, a 401 for `/api/`. `app/page.tsx` is the server component: it fetches `GET /api/v1/me` and the dashboard in parallel with the token from `app/lib/session.ts`, and projects both into the props of `app/DashboardClient.tsx`, the `"use client"` UI. **Nenhum caminho da tela fabrica resposta ou citação** (ADR 0021): um 429 vira a mensagem de ritmo com os segundos do `Retry-After`, qualquer outra falha vira "não consegui falar com o assistente, nada foi registrado", e o `answerFor()` que inventava data, decisão e rótulo de citação no `catch` foi apagado — junto da asserção que exigia sua existência. A guarda de `rendered-html.test.mjs` agora é sobre a forma: um array de literais atribuído a `sources` no cliente do chat reprova, porque toda citação verdadeira vem da API. The frontend's role is BFF: it never decides authorization.
- **`apps/api/`** — FastAPI (`portal_api`), Python 3.13, Pydantic settings. `main.py` holds the REST contracts under `/api/v1`. Every client endpoint depends on `CurrentPrincipal` (`auth.py`), which validates the OIDC access token against the realm's JWKS; `identity.py` turns that principal into a `user` row (link by e-mail on first login, provision if unknown) and `access.py` decides what the user reaches — always `None` → 404, never 403.
- **`apps/api/src/portal_api/{db,models,repositories}/`** — the Postgres data layer (SQLAlchemy 2.0 + Alembic). Models live in the `portal` schema, but the metadata is **not** schema-qualified: the engine pins the connection `search_path` to `portal,public` (`db/session.py`) so DDL and reflection stay unqualified and `alembic check` sees no false drift — keep new models unqualified too. `public` is there only for pgvector's `vector` type, which the bootstrap creates in that schema; `portal` stays first, so an unqualified table still lands in it. `db/base.py` provides `TenantMixin` (adds `organization_id`; project tables also add `project_id`). Data access goes through `repositories/`: `TenantScopedRepository` filters every read and stamps every write from a `TenantContext`, enforcing org/project isolation at the app layer — the barrier *before* RLS, which is the second one below it.

## Tenancy and the database roles (ADR 0010)

Three credentials, one per kind of work, and `DATABASE_URL` is the request path:

| Setting | Role | RLS |
|---|---|---|
| `DATABASE_URL` | `portal_app` — API and worker request path | **subject to it** |
| `DATABASE_SYSTEM_URL` | `portal_system` — Biahflow webhook, sync, seed | `BYPASSRLS` |
| `DATABASE_MIGRATION_URL` | `portal_migrator` — owns the schema, runs Alembic | exempt as owner |
| `DATABASE_ADMIN_URL` | `portal_admin` — `/api/v1/admin/*`, the only writer of `membership` | **subject to it** |

`get_session(principal)` publishes the tenant context as transaction-local GUCs, in two stages: identity (`portal.subject`, `portal.email`, `portal.user_id`) and tenant (`portal.organization_id`, `portal.project_id`). The policies read those, and `current_setting(..., true)` returns NULL when unset — so **missing context yields zero rows, never an unscoped read**. `access.scoped_project`/`default_project` call `bind_tenant` themselves; if you add a resolver that returns a project, it must do the same or every later read comes back empty (`docs/runbooks/auth-failure.md`).

**Writing `membership` goes through `portal_admin` and nothing else (ADR 0011).** Its policies key on a third-stage GUC, `portal.admin_organization_id`, which `bind_admin_org` publishes *after* the caller's `internal_admin` was verified — before that the transaction sees only the caller's own memberships, which is what keeps the check from being circular. A fourth GUC, `portal.invitee_subject`, opens exactly one `user` row: the person being invited. Every admin policy is `TO portal_admin`, so the request credential is not merely missing the grant — the policy does not apply to it.

**Every new table carrying `organization_id` ships with a policy in the same migration.** A meta-test in `test_rls_isolation.py` fails CI otherwise. The app role holds `SELECT` almost everywhere, `INSERT` only on `pending_item`, `audit_log` and `agent_event` (the last one added in Fase 3 with a `WITH CHECK` on the tenant — the ingestion route is the only one that takes a project id from outside, so it is exactly where RLS has to stay as the second barrier; `agent_api_key` grants it nothing at all), `INSERT` plus a **column-scoped** `UPDATE (external_subject, notify_by_email, updated_at)` on `user`, and on `notification` a column-scoped `UPDATE (read_at, updated_at)` and nothing else — mirroring "the portal never originates status" (ADR 0006/0008) in the database itself. The column grants are the point: a policy decides which *rows*, never which *columns*, so "mark as read" and "change my e-mail preference" cannot become "rewrite the notice" or "promote myself to internal staff" (ADR 0012). Fase 4's index added no write at all to the app role: `document_chunk` is SELECT-only for it, and `document` gained `INSERT/UPDATE/DELETE` for `portal_admin` alone (ADR 0014). `organization_retention_policy` and `data_erasure_request` follow the same shape (ADR 0017), and `portal_admin` holds `SELECT, INSERT` on the request with **no `UPDATE`** — whoever asked does not rewrite the record of what was asked, and the worker that did the work is what stamps the result. `project_drive_connection` goes further and gives `portal_app` **no policy at all** (ADR 0016): the app role still inherits `SELECT` from `roles.sql`'s default privileges, but no policy is `TO portal_app`, so the read returns zero rows — the same "the rule is not about you" shape as `agent_api_key`, and what keeps the refresh token away from the request path. The conversation is the one place where that rule inverts (ADR 0015): `portal_app` gets `INSERT` on `conversation`/`conversation_message`, because there it *originates* the row — the question is the user's — instead of reading what someone else produced. What replaces the guarantee is an invariant, not a privilege: **`conversation_message` is never a retrieval source**, `ai/retrieval.py` does not read it, and an eval runs the obvious attack. The feedback is column-scoped like `read_at` before it — `UPDATE (feedback, feedback_comment, feedback_at, updated_at)` — so a person rates the answer and can never rewrite the answer or the citations it showed. Fase 5 acrescentou três colunas de carimbo à mesma linha (`prompt_version`, `responder`, `model`; ADR 0021) e **nenhum GRANT novo**, exatamente porque o `INSERT` já existia e o `UPDATE` de coluna continua onde estava: ninguém reescreve qual prompt produziu a resposta, pela razão de ninguém reescrever as citações. `chat_rate_window` é a exceção que confirma o meta-teste: **não** tem `organization_id`, então ele não a cobra — o limite é de uma pessoa, não de um tenant —, e ela fica com RLS ligada e nenhuma policy `TO portal_app`.

`notification` is the one table whose row belongs to a *person*: its policies add `user_id = portal.current_user_id()` to the tenant predicate, and nobody but `portal_system` inserts there — the sync is the producer, because the portal cannot know that something *changed* except by diffing the read model around a snapshot.
- **`apps/api/src/portal_api/{crypto,drive_sync}.py` + `integrations/google_drive.py`** — the Drive connector (ADR 0016). `crypto.py` is the portal's only **reversible** secret: a refresh token has to be replayed to Google, so HMAC cannot work, and it is sealed with AES-256-GCM whose AAD carries the tenant — a ciphertext moved to another project fails to open. The adapter speaks Drive v3 over `httpx` (no SDK) and is pure transport; `drive_sync.py` is the only place the index is reconciled, and it holds the three invariants: it removes **only** over a complete listing (a partial one describes a smaller Drive than the real one), it only ever touches `origin='drive'`, and two gates — `modifiedTime`, then the SHA-256 — keep an idle folder from costing a single PUT. A shortcut is skipped, never followed.
- **`apps/api/src/portal_api/worker.py`** — Celery worker for async jobs (Drive/document ingestion, the notification digest), gated on Redis. Since Fase 4 it also carries the project's first `beat_schedule`; the `beat` service is **singleton**, and the overlap guard is a conditional `UPDATE` on the connection row, not a Redis lock. `send_project_digests` works off `emailed_at IS NULL` rather than an id list from the caller, so a re-delivered task is a no-op and a lost one is only a delay. Enqueueing is wrapped in `queue_project_digests`/`queue_pending_notification`, which swallow a dead broker: the notifications are already committed and show up in the portal either way.
- **`apps/api/src/portal_api/notifications.py`** — the only place a `Notification` is created (ADR 0012). `snapshot_state` photographs the read model *before* `sync_snapshot` writes, `diff` compares, `fan_out` inserts one row per recipient with `ON CONFLICT DO NOTHING`. Adding a new kind of notice means adding a `NotificationKind`, a branch in `diff` with a stable `dedupe_key`, and an entry in `AUDIENCE` — nothing else.
- **`apps/api/src/portal_api/conversations.py`** — the only place a conversation turn is written (ADR 0015), in the same shape and for the same reason as `notifications.py`: if "who records what the client typed" is spread around, the question stops having an answer you can read in one file. Two functions — `append_turn` and `record_feedback` — and no function that edits a message, which is not an omission: the column grant would refuse anyway. An unknown (or someone else's) `conversation_id` opens a new thread rather than 404-ing, because the turn was already answered by the time the write happens. Nothing here flows back into retrieval.
- **`apps/api/src/portal_api/agent_auth.py`** — the only alternative to OIDC on a client route (ADR 0013). Resolves `X-Agent-Key` under `portal_system` (the lookup happens *before* there is a tenant to bind — the tenant comes out of the key), then the ingestion runs in a second transaction under `portal_app` with `bind_tenant`. Every credential refusal is the same opaque 401 with the reason in the log; only the rate-limit window answers 429, because the producer has to tell pace from credentials. In its own module for the same reason `admin.py` is: "what authenticates an agent" should fit in one file.
- **`apps/api/src/portal_api/{storage,ingestion/,ai/embeddings}.py`** — the path a file takes to become citable evidence (ADR 0014). `storage.py` speaks S3 (MinIO locally), and the object key carries the whole tenant. `ingestion/extract.py` turns bytes into pages and `ingestion/chunk.py` turns pages into chunks — both pure, no DB and no network, and both obeying the one rule the citation rests on: **a chunk never spans a page boundary**, because "página 3" is either true or it is noise wearing the clothes of a source. `ai/embeddings.py` mirrors `ai/responder.py`: Voyage when `VOYAGE_API_KEY` is set, a deterministic hashing projection otherwise, same dimension either way. The distance cutoff belongs to the embedder, not to the retriever — the two vector spaces are different, and one number would serve both badly. Writing the index is the worker's job under `portal_system`; `portal_app` is SELECT-only on `document_chunk`, because a request path that can write a chunk can write the "evidence" it wants cited. `scanner.py` (Fase 5, ADR 0017) sits **between** the object and the parser, because extracting text already means opening the bytes with an analyzer: ClamAV over a raw socket when `CLAMAV_HOST` is set, and otherwise a path that recognizes the EICAR test string and answers `skipped` for everything else. **`skipped` is not `clean`** — an absent scanner does not get to assert the file is safe, which is the same rule rule 3 of `AGENTS.md` imposes on the assistant. `scan_state` is its own column rather than another `ingest_state` value: "is it safe" and "did it become citable text" can disagree on the same document. `queue_document_scan` is the single door — upload, `reindex_project` and the Drive sync all go through it — and `ingest_document` refuses anything unscanned on its own, the same twice-checked boundary as the Drive folder.
- **`apps/api/src/portal_api/ai/prompt.py` + `docs/ai/prompt-registry.json`** — o prompt e o nome dele, no mesmo arquivo (ADR 0021). `PROMPT_VERSION` mora acima do `SYSTEM_PROMPT` porque uma versão que mora numa variável de ambiente é uma afirmação que o deployment faz sobre um texto que ele não contém — era o que havia até a Fase 5, e ninguém lia. O portão é um **registro append-only** de três digests (prompt, esquema de saída e a *moldura* do prompt do usuário; nunca o conteúdo, que mudaria a cada requisição) com `--record` que **recusa** reescrever versão já gravada: é o terceiro gate de deriva do repositório, ao lado do `alembic check` e do `openapi.json`, e é registro em vez de constante porque uma constante deixaria passar justamente quem atualiza texto e digest juntos sem trocar a versão. `ai/responder.py` ganhou `anthropic_client()` — o ponto de costura, na forma do `session_client` do Drive — sem o qual o `AnthropicResponder` e o `SYSTEM_PROMPT` seriam código que nenhum teste executa, que era o estado até aqui. **A moldura ganhou data na ADR 0038, e a sentinela do digest teve de ganhar junto**: acrescentar a data à linha da evidência **não mudou** o `template_sha256`, porque `_TEMPLATE_SAMPLE` não tinha `dated_at` e percorria só o ramo antigo — a cobertura de um portão é a dos ramos que a amostra percorre, e a amostra é parte do portão. São duas sentinelas agora, uma datada e uma não.
- **`apps/api/src/portal_api/ai/quota.py` + `preflight.py` + `scripts/loadtest.py`** — o teto da conta, a recusa de subir inseguro e a medição (ADR 0022). `ai/quota.py` é o único lugar onde gasto de IA é contado e cobrado, na forma de `notifications.py` e `chat_limit.py`; o razão (`ai_usage_event`) guarda **tokens e nunca dinheiro**, e o custo nasce na leitura pelo preço vigente **no dia da chamada** (`ai_model_price`, com `EXCLUDE USING gist`) — literalmente `results.py`, porque reajustar o preço hoje não pode reprecificar março. **Não é um contador incrementado**, e quem disse isso foi o docstring do `chat_limit.py`: aquele contador subconta sob concorrência, o que "seria inaceitável para um contador de faturamento". Um `INSERT` por chamada não disputa; a soma é um `SUM`. Sem preço vigente o turno **passa** e a lacuna é declarada — a única falha aberta do repositório, por assimetria de recuperação. A recusa é 429 (403 não existe aqui) e vem **depois** do 404, ao contrário da janela de taxa, e não deixa rastro: sem pendência, mensagem nem consumo. `preflight.py` é a outra metade do par `${VAR:?}` do `docker-compose.homolog.yml`: o compose recusa a variável ausente, e ele recusa a variável *presente valendo o exemplo* — varredura genérica sobre as settings, para uma setting nova com default local já nascer coberta. `scripts/loadtest.py` mora em `scripts/` pela razão do backup (é operação), tira o custo do mesmo razão que a quota usa, recusa rodar com chave e sem `--budget-usd`, e **declara no relatório o que mediu**.
- **`apps/api/src/portal_api/chat_limit.py`** — com que ritmo uma pessoa pode perguntar (ADR 0021), em módulo próprio pela razão de `agent_auth.py` não morar em `auth.py`. Janela na linha, em Postgres e não em Redis (a API sobe sem broker), numa tabela `chat_rate_window` **sem tenant** — o limite é de uma pessoa, e por projeto deixaria alguém multiplicar a cota abrindo projetos — com RLS ligada e nenhuma policy `TO portal_app`, a forma de `agent_api_key`. O `consume` roda sob `portal_system` em transação **anterior** à do chat, e o motivo é lock e não estilo: `identity.resolve_user` escreve em `user` dentro da transação do chat, que abrange a chamada ao modelo, então a janela ali travaria o primeiro login. Deliberadamente **não** unificado com o `_check_window` de `agent_auth.py`: chaveiam coisas diferentes e fundi-los faria "o que autentica um agente" deixar de caber num arquivo.
- **`apps/api/src/portal_api/search.py` + `textfold.py`** — a busca do projeto, e a dobra que ela e o índice fazem igual (ADR 0024). `search.py` é o único lugar onde um termo digitado vira linhas, na forma de `notifications.py` e `retention.py`: a consulta nasce em cinco repositórios, e espalhá-la faria "o que a busca alcança" deixar de caber num arquivo — que é a pergunta de quem revisa isolamento. O filtro de tenant **não** sai de lá: `TenantScopedRepository.matching()` aceita o predicado e continua aplicando `_tenant_filters()` por dentro, senão a primeira barreira estaria reimplementada noutro arquivo e uma divergência entre as duas passaria despercebida (a RLS continuaria certa, e o teste de isolamento, verde). Duas fontes — linhas do read model por título e trechos de `document_chunk` por full-text —, e a segunda é a que faz "buscar no contexto do projeto" valer para o conteúdo do contrato e não só para o nome dele. `textfold.py` é folha pela razão de `scanner.py` ser uma, e existe porque a mesma expressão aparece em três lugares que têm de ser idênticos ou o índice deixa de ser usado **sem nada ficar vermelho**: o `Index` do modelo, o `CREATE INDEX` da migração 0019 e a consulta. Sem `unaccent`: extensão é objeto de *banco*, não entra num `pg_dump -n portal` e teria de nascer no bootstrap, no init e na migração — o defeito que a ADR 0019 achou no `btree_gist` no dia do restore —, e ainda é `STABLE`, o que exigiria uma função `IMMUTABLE` própria. Só entra o que alguma aba mostra — regra que teve **uma** exceção nomeada por três fases, `Decision` com modelo desde a Fase 1 e nenhuma aba, fechada na ADR 0049 quando o escritor nasceu no Biahflow (FDD 032 de lá) e a decisão passou a casar por título **e racional**, o termo digitado **nunca** vai para o log nem para `audit_log`, e não há limite de taxa — a busca é uma consulta ao Postgres, e pôr limitador onde não há recurso escasso é o que faz o limitador do chat parecer arbitrário.
- **`apps/api/src/portal_api/results.py`** — the read-time computation. Nothing is derived on write: the event stores the integers the agent reported, and money is produced by applying the assumption in force **on the day of the event**, so raising the hourly rate today cannot reprice March. Missing basis yields `None` plus a reason in `gaps` — zero investment declares the gap instead of dividing by zero. Adding an indicator means adding it here and to `to_payload`, never to the ingestion.
- **`apps/api/src/portal_api/telemetry.py`** — o único lugar onde o `trace_id` nasce, é lido e é formatado (ADR 0018), na mesma forma de `notifications.py` e `conversations.py`. O `JsonFormatter` é de biblioteca padrão e a parte que importa dele não é o JSON: é derivar os campos de `extra` por diferença com os atributos de um `LogRecord`, que é o que faz `auth.rejected` finalmente imprimir o `reason` que ele já carregava. Ele **redige** campos com nome de segredo, com `key_prefix` numa allowlist obrigatória — sem ela o runbook da API de eventos voltaria a mandar ler um campo que não sai. O `TraceMiddleware` é ASGI puro (o `BaseHTTPMiddleware` põe um task group entre onde a `ContextVar` é escrita e onde é lida), guarda o **template** da rota e nunca o path resolvido, e ecoa o header. `audit_data()` carimba o id no JSONB que já existia. No web o par é `app/lib/trace.ts` (memoizado com o `cache()` do React, para as três `fetch()` paralelas do SSR saírem com um id só) e `app/lib/log.ts`; o id entra na API por `authorizationHeader()`, que é o ponto de costura que o resto deste arquivo já mandava usar. **Não** nasce no `proxy.ts`, e o preço está declarado no ADR.
- **`apps/api/src/portal_api/schemas.py` + `openapi.py` + `docs/api/openapi.json`** — o contrato do cliente declarado num lugar só (ADR 0020), na mesma forma de `notifications.py` e `telemetry.py` e pelo motivo inverso ao de `admin.py`: lá a resposta nasce ao lado da rota, aqui ela nasce em `build_dashboard`, `results.to_payload` e `_message_payload`, e o modelo junto de cada produtor reproduziria a divisão que o módulo fecha. Duas regras: **onde o produtor já entregou texto, o modelo declara texto** (um `.isoformat()` fica `str`, senão o Pydantic reserializa e a fatia muda o byte que prometeu não mudar); e **`extra="forbid"`**, porque o padrão do `response_model` *filtra em silêncio* o campo que o modelo não conhece — tipar as respostas acrescentaria ao repositório o defeito de um dado sumir da tela com a rota respondendo 200. O esquema é gerado por `python -m portal_api.openapi --write` e versionado; `test_openapi_contract.py` é o `alembic check` dele, e as asserções que importam não conferem campo, conferem **regra** sobre toda rota — ninguém declara 403, rota autenticada declara 401, rota escopada declara 404, só a de eventos aceita chave, nenhum campo de resposta tem nome de segredo (pela lista de `telemetry.py`, reusada e não recopiada). Os três `securityScheme` são declarativos com `auto_error=False`: não decidem nada, e não podem — o `HTTPBearer` de erro automático responde 403, que aqui não existe.
- **`scripts/audit.mjs` + `docs/security/advisories.json`** — o portão de dependências vulneráveis, nos dois ecossistemas (ADR 0023). Em `scripts/` pela razão do `backup.sh` e do `loadtest.py`: é operação. Uma porta só para `npm audit` e `pip-audit`, na forma do `queue_document_scan`, com núcleo puro (`evaluate(findings, registry, today)` — o dia entra por parâmetro, como em `results.py`) e as bordas impuras no entry point. Duas coisas medidas mandam nele: a versão que um aviso nomeia pode não bastar (o `next@16.2.12` fechava os nove avisos dele e repinava `postcss` e `sharp` vulneráveis; só a 16.3.0 zera), e um aviso em transitiva do FastAPI se conserta **subindo o FastAPI** — mas só em instalação limpa, porque a faixa nova é `>=` sem teto e um ambiente que já tinha o `starlette` vulnerável continua nele. Daí o pin direto de `starlette`, com o precedente e o argumento que o `cryptography` já tinha escrito no `requirements.txt`.
- **`apps/api/src/portal_api/backup.py` + `scripts/`** — o backup, e a única parte do repositório que não é web, API nem infraestrutura declarativa: é operação (ADR 0019). O módulo cuida só dos **objetos** — duas funções, nenhuma rota HTTP, mesma regra da `retention.py` —, e o tar leva a chave do objeto como nome de membro, porque a chave já carrega o tenant inteiro desde a ADR 0014. O banco é `scripts/backup.sh`, e o que ele fixa é o que o Postgres provou ser necessário: **o dump não sai com `portal_app`**, que a RLS faz o `pg_dump` recusar — e o `--enable-row-security` que cala a recusa devolve um backup limpo, bem-sucedido e vazio. Daí o par de credenciais deliberadamente diferentes: o dump sob `portal_migrator` (dono, isento por ser dono) e o **censo de linhas sob `portal_system`**, senão os dois erram na mesma direção e o manifesto confirma que zero virou zero. `restore.sh` roda o `roles.sql` **antes** do `pg_restore` (papel é objeto de cluster, extensão é objeto de banco, e nenhum dos dois entra num `pg_dump -n portal`) e afirma com código de saída que `portal_app` continua sem `BYPASSRLS` e que as policies voltaram. A cifra é `age` e a ausência da chave **falha** — `skipped` não é `clean`, aqui também.
- **`apps/api/src/portal_api/retention.py`** — the only place data is deleted by age (ADR 0017), in the same shape and for the same reason as `notifications.py` and `conversations.py`. Two operations that must not be confused: the **purge** is by age, runs on the beat and never touches a `document` — a document is the evidence behind a citation already given, and deleting it on an anniversary would make an old answer impossible to check. The **erasure** is somebody's decision, recorded in a row, and it takes everything including the storage objects under `org/<id>/`. A null column in `organization_retention_policy` means "use the default", never "keep forever". The erasure request row **survives its own erasure**: wiping a tenant without recording that you did makes "what happened to that organization" unanswerable, which is exactly the question someone asks later. No HTTP route deletes anything — `portal_admin` writes the intent, the worker under `portal_system` carries it out, which is what ADR 0015 decided when it deferred the subject.
- **`apps/api/src/portal_api/grant_access.py`** — o primeiro vínculo de uma organização, e só ele (ADR 0025). Existe por uma lacuna que só apareceu quando a **segunda** organização passou a existir: a ADR 0011 fechou a escrita de `membership` em `portal_admin`, e `admin.py` exige já ser `internal_admin` naquele projeto — o que é circular por desenho e não tinha saída para a organização que o sync do Biahflow acabou de criar, que nasce com zero membros e fica invisível para todo mundo. **Não é rota, e é isso que o torna aceitável**: uma rota capaz de criar o primeiro administrador de um tenant é a porta que a ADR 0011 fechou, com outro nome — mesma simetria da ADR 0017, onde nenhuma rota apaga um tenant. Roda sob `portal_system` pelo argumento do `seed.py` (inaugura tenant, não há contexto a fixar), concede vínculo **organizacional** (`project_id IS NULL`, senão o bootstrap se repetiria a cada projeto novo do Biahflow), é idempotente, grava `audit_log`, e **recusa quando a organização já tem `internal_admin`** — a partir daí o caminho é o `/admin`, e um comando que continua servindo depois de desnecessário vira o caminho preferido por conveniência.
- **`apps/api/src/portal_api/seed.py`** — the local seed, run by the `api-seed` compose service. Its `SEED_USERS` carry the same UUIDs the realm import fixes as user ids, which *are* the `sub` claim, so a seeded row already knows its `external_subject`. `test_seed_matches_realm.py` fails the build if the two drift. The project data enters through `sync_snapshot()` with a versioned snapshot — the webhook's own door, so the portal still originates no status (ADR 0006/0008).

There is exactly one data layer: the FastAPI service owns PostgreSQL+pgvector (source of truth, RLS per org/project). The web layer is stateless — it holds no database of its own.

## The session (ADR 0010)

The BFF is a **confidential** OIDC client. The authorization code is exchanged on the server and the access token is stored in the encrypted Auth.js cookie — never in the `session` object, so it cannot reach a client bundle or an RSC payload. `app/lib/session.ts` is the only way to read it back; a new server-side call to the API takes its `Authorization` header from `authorizationHeader()`.

**Two URLs for one Keycloak, and they are not a mistake.** The browser reaches it at `KEYCLOAK_ISSUER` (`localhost:8080`), and that address is the `iss` of every token, which is what the API validates against `OIDC_ISSUER`. The containers reach it at `KEYCLOAK_INTERNAL_URL` (`keycloak:8080`), which is where the token exchange and the refresh go. `auth.ts` passes both endpoints explicitly, which also skips OIDC discovery — discovery would refuse the mismatch. The API mirrors the split with `OIDC_ISSUER`/`OIDC_JWKS_URL`.

Roles are deliberately **absent** from the session: a realm role cannot say *which project*, so the UI reads them from `GET /api/v1/me`, which answers from the membership.

Demo data has exactly one door left, `demoShellEnabled()` in `app/lib/demo.ts`: no `API_BASE_URL` **and** `DEMO_MODE=true`. It is the only exception in `proxy.ts`, and a test asserts that `DEMO_OVERVIEW` is unreachable outside that gate. Do not widen it.

## Styling

Tailwind CSS v4, configured entirely in `app/globals.css` (no `tailwind.config.js`). The `@theme` block is the single source of design tokens — brand scale (`brand-50…900`, the Portal Labs purple), `ink`/`muted`/`line`/`canvas`/`navy`, state colors and the layered shadows. Recurring UI (`.panel`, `.nav-item`, `.milestone`, `.journey-*`, …) lives in `@layer components` built from Tailwind utilities via `@apply`, so the markup stays readable and the tokens stay authoritative; the three responsive breakpoints (761px collapsed sidebar, 980px, 760px mobile) are plain media queries at the end of the file. Never hardcode a hex in a component — add or use a token.

## Non-negotiable rules (from `AGENTS.md`)

1. Every datum belongs to an organization **and** a project. Never trust a client-supplied identifier without server-side validation of the membership link.
2. Never send secrets, tokens, system prompts, or another project's context to the AI model.
3. AI answers must cite sources. With no evidence, declare the gap and create a pending item (`pendência`) — never invent an answer.
4. Migrations are additive and reviewed. Changes to tenancy, auth, RAG, or retention require an ADR/RFC (`docs/adr/`, `docs/rfc/`).
5. Never put secrets in commits, fixtures, logs, or documentation.
6. Every new endpoint or search ships with a negative-permission test case, and it asserts 404 — never 403.

**This list is `AGENTS.md`'s, item for item, and a guard asserts it** (`test_agents_rules.py`, ADR 0035). Until then it was a *renumbered* copy: it promoted a convention ("the frontend does not decide authorization" — still true, still a convention, see `AGENTS.md` § Convenções) and a PR-checklist item to principles, and **dropped rule 5 entirely**. That numbering is the one that leaked — two ADRs, one FDD and three test files cite "regra 6 do `AGENTS.md`", a number that did not exist, and `docs/adr/0025` calls "regra 5" something different from what `docs/adr/0018` calls it. The guard also fails a `regra N` citation that points past the end of the list.

`docs/runbooks/integracao-biahflow.md` liga o Biahflow **de verdade** (os dois lados já implementam a ADR 0006 / ADR 0003 de lá): dois segredos pareados, `host.docker.internal` nos dois sentidos porque são dois projetos Compose, e o bootstrap da ADR 0025. Traz também os tropeços medidos ao percorrê-lo, nas duas passagens (05 e 06/08/2026) — `DJANGO_ALLOWED_HOSTS` sem o nome que o contêiner usa (Django responde 400, o portal transforma em 500, e um `curl` da máquina funciona porque manda outro `Host`), migração pendente derrubando o snapshot, e o fato de que **cadastrar um funcionário digital não emite webhook**: não há receiver de `DigitalEmployee` no `signals.py` de lá, então o time digital só chega no próximo save de outra coisa. O item da **jornada** dizia o mesmo e deixou de ser verdade — os receivers de `ProjectPhase` e `ProjectDeliverable` existem, com um `if created: return` que impede a criação de um projeto de disparar dezenas de webhooks —, e a retificação ficou registrada em vez de a frase ser apagada, junto do erro de nome que ela carregava: `PhaseDeliverable` é o template global, e não ter receiver nele está certo. Mais duas armadilhas de operação: um `manage.py shell -c` termina antes da thread daemon do `emit`, e o webhook não sai **sem erro nenhum**; e um 500 isolado com `RemoteProtocolError` é a primeira conexão ao `runserver` ocioso, não `ALLOWED_HOSTS`. **O tropeço (e) foi o único achado por alguém usando o produto, e virou a ADR 0036**: arquivar um projeto lá o tirava da rota de snapshot, então o portal levava 404 — indistinguível de "este id nunca existiu" — e mantinha na tela do cliente, como ativo, um projeto encerrado, por todo o tempo que o arquivamento durasse. Agora o snapshot responde 200 e declara `archived_at`, o portal tem coluna própria para isso (**não** um valor de `ProjectStatus`: encerrado e "em implementação" são fatos diferentes, e o segundo apagaria o primeiro ao restaurar), a tela marca "Projeto encerrado" mantendo o histórico inteiro, e `POST /chat` e `POST /me/pendings/{id}/comments` respondem **409** — não 404, que neste contrato significa uma coisa só e cuja corrupção faria um cliente legítimo receber a mesma resposta de um estranho. **E o irmão do (e) virou a ADR 0037**, cuja promessa quebrada estava escrita no outro repositório e em negrito — "o que entra no snapshot precisa de emissor, sob pena de o portal exibir um estado que já mudou" (ADR 0003 de lá): `digital_employees` entrava no snapshot sem emissor nenhum, e **arquivar** um funcionário digital era o pior dos três caminhos, porque tira a linha do snapshot e o roster do cliente continuava exibindo quem a fonte já tinha tirado. A medição **encolheu o diagnóstico** que a ADR 0036 deixou: o `DELETE` da API de lá arquiva (os nove viewsets são `ArchiveModelViewSet`), o Django admin não registra entidade de projeto, e `retention.executar()` só alcança linha já arquivada — que já saiu do snapshot e já foi propagada. Sobrava um caminho, e ele é total: `Project.delete()` por shell deixava o portal com um projeto morto marcado como **ativo para sempre**. Agora há `post_delete` de `Project` — o único de lá, e a cascata inteira sai como **um** aviso —, `event` ganhou deste lado **o primeiro leitor que já teve** (o campo existe desde a ADR 0006 e ninguém o lia; a forma da guarda da ADR 0033 na direção de entrada, onde não há guarda porque o produtor é outro repo), e `source_deleted_at` é coluna separada de `archived_at` porque as duas chegam por portas diferentes: arquivamento vem no snapshot e o sync o reescreve a cada passagem, exclusão chega só pelo webhook — numa coluna só, o sync apagaria o fato. O portal **não apaga nada**: documento é evidência de citação já dada, e apagar tenant é decisão de pessoa executada pelo worker (ADR 0017). Fica aberto: exclusão de **filho** continua sem aviso, agora com o argumento medido de por quê, e um `deleted` perdido é definitivo — não haverá evento seguinte daquele projeto.

With the stack up, `docs/runbooks/passeio-local.md` is the walkthrough: the three seeded accounts (all `portal_local_only`), and the path to see every slice working — including the two operations that live outside this repository and had their commands buried in e2e specs, the Biahflow `sync_snapshot` and the agent event. It also records what the local environment does *differently* and why (offline responder without `ANTHROPIC_API_KEY`, `scan_state=skipped` without ClamAV), so that none of it gets reported as a defect.

CI (`.github/workflows/ci.yml`) runs seven gates you should reproduce locally before a PR: `web-quality` (lint + test), `api-quality` (pytest, minus the backup file), `backup-restore` (that file, with Postgres **and** MinIO **and** the four role passwords — its own job because a broken backup deserves its own red), `local-stack` (`docker compose config --quiet` + `docker compose build`, mais as duas asserções sobre o override de homologação — que ele **recusa** sem segredos e valida com `.env.homolog.example`; ADR 0022), `e2e` (the whole compose stack + Playwright, mais um smoke de quinze segundos do `scripts/loadtest.py` que existe para a ferramenta não apodrecer, nunca como medição), `dependency-audit` (`npm run audit` nos dois ecossistemas, job próprio pelo argumento do `backup-restore` e rodando em `push` **e** `pull_request`; ADR 0023), plus dependency-review — que **não se sobrepõe** ao anterior: ele olha o *diff* de dependências de um PR e pega a biblioteca ruim entrando, o `dependency-audit` pergunta o que já está instalado. Confundir os dois é o que deixou nove avisos do `next`, sete do `starlette` e seis do `python-multipart` passarem verdes a cada push. **Ele está desligado por variável desde 17/08/2026**, e não por escolha: ao migrar para a org `biahflow` o repositório passou a privado, e ali a API de dependency review exige Advanced Security — o job reprovava com "not supported on this repository", que é sobre o plano e não sobre as dependências do PR. O que se perde está declarado no próprio job: some o portão sobre o *diff*, fica o `dependency-audit`. Only `codeql` and `dependency-review` do not gate, and neither by choice: it cannot pass until code scanning is enabled in the repository settings (a private-repo account setting, not a workflow one), so it is **skipped by variable** rather than red or commented out. `e2e` stopped being `continue-on-error` in ADR 0020 — along with the self-skipping specs, it was the second of two independent mechanisms guaranteeing the one level that proves login end to end could never fail a PR. Every job has a `timeout-minutes`: a hang used to hold `web-quality` for the runner's full six hours, and a stuck job keeps the whole run from publishing logs — hiding why the *other* jobs failed.

**`CI` in the environment changes what a skip means.** `skip_unless_ci` (`apps/api/tests/conftest.py`) and `stackIsMissing` (`tests/e2e/stack.ts`) skip on a developer's machine and **fail** under CI, because there a skip does not say "cannot prove this here" — the job *has* a Postgres, the job *boots* the stack — it says the environment is not what someone assumed, in green. That is how the three assertions carrying the backup (ADR 0019) went weeks without running. It applies only to what CI is supposed to cover; ClamAV and a Voyage key still skip quietly, because there the skip is still true.

## Conventions

- REST under `/api/v1`; Pydantic payloads and standardized errors. **A new client route ships with a `response_model` from `schemas.py` and `responses=CLIENT_ERRORS`**, and the schema artifact is regenerated in the same commit (`python -m portal_api.openapi --write`) — `test_openapi_contract.py` fails otherwise, and it also fails a route that declares 403 or a response field named like a secret.
- **Prometeu 404, prova o 404** (ADR 0035). `test_authorization.py` deriva do contrato publicado a lista de rotas que declaram 404 e cobra, de cada uma, um teste que troque de ator e afirme a negação — a regra 6 do `AGENTS.md`, que até aqui era a única inegociável sem portão derivado (30 funções à mão contra 46 pares rota+método). Quem legitimamente não nega por tenant não declara 404 e se isenta sozinho; a ligação é entre o 404 e **a resposta daquela chamada**, e não com o corpo do teste, porque o elo frouxo foi medido dando `POST /chat` como coberto por um 404 que era de outra rota.
- **Mexeu no prompt, muda a `PROMPT_VERSION`** (ADR 0021). Alterar o `SYSTEM_PROMPT`, o `OUTPUT_SCHEMA` ou a moldura de `build_user_prompt` sem trocar a versão reprova em `test_prompt_version.py`, e **regravar o registro não conserta** — `python -m portal_api.ai.prompt --record` recusa reescrever uma versão já gravada. É o terceiro gate de deriva, ao lado do `alembic check` e do `openapi.json`. Mudança de prompt, recuperador, modelo ou ferramenta também pede eval (`docs/ai/eval-dataset.md`), e a seção adversarial é a que roda contra o respondedor real — com o cliente injetado pelo ponto de costura, **sem chave e sem custo de token**.
- Web tests assert against **server-rendered HTML** (`tests/rendered-html.test.mjs` boots `next start` and matches strings like the page title and dashboard copy). If you change dashboard text/structure, update these assertions. The second test scans every source file under `app/` and `components/` to guard against reintroducing hardcoded tab data (the Fase 2 regression) and starter leftovers.
- **A mensagem do log é o nome do evento; o detalhe vai em `extra`** (ADR 0018/0034).
  `familia.acontecimento`, sem interpolação — o `JsonFormatter` põe a mensagem **já interpolada**
  no campo `event`, então um `logger.warning("Objeto %s não removido", key)` gera um `event`
  diferente por ocorrência e o limiar que `runbooks/alerts.md` promete deixa de valer.
  `test_telemetry.py` varre o AST e reprova; a allowlist é só para os comandos de operação
  (`seed`, `preflight`, `backup`, `grant_access`), cujo leitor é uma pessoa no terminal.
  **E o evento novo ganha linha no `alerts.md` no mesmo commit** — a guarda é bidirecional, porque
  as duas direções já falharam: a ADR 0028 achou o runbook nomeando um evento que ninguém emitia,
  e a ADR 0034 achou doze emitidos que o runbook não conhecia. Quem não merece limiar entra em
  `NOT_AN_ALERT` com o motivo escrito. **A varredura cobre os dois deployables** (ADR 0035): o BFF
  tem logger estruturado próprio (`app/lib/log.ts`) e seus quatro eventos — `api.rejected`,
  `api.unreachable`, `api.failed`, `web.request_error` — não tinham linha em runbook nenhum,
  porque a guarda parava na fronteira do pacote Python. É uma guarda só, e não um teste node ao
  lado, porque o `alerts.md` é um arquivo só e duas guardas sobre ele divergem.
- Access administration lives in `portal_api/admin.py` (an `APIRouter`), never in `main.py`: it is the only surface that runs under `portal_admin`, and keeping it apart is what makes "who can write membership" answerable by reading one file.
- Agent keys, financial assumptions, document upload and the Drive connector live in `admin.py` too, for the same reason: they are the write path under `portal_admin`. `POST /api/v1/admin/drive/callback` is the one route there without a `{project_id}` — the project comes out of the row found by the OAuth `state`, the same way ADR 0013's tenant comes out of the key instead of the body. A plaintext key is returned exactly once, at creation; nothing anywhere can recover it afterwards. The upload is the only route that speaks multipart, and the only one where the row is written *before* the side effect (the object key needs the row's id) — so a dead storage rolls the transaction back instead of leaving a `document` pointing at a file that does not exist. **As rotas cujo escopo é a *organização* — retenção, teto de IA e apagamento — moram lá pelo mesmo motivo, e desde a ADR 0027 têm caller:** elas são chaveadas por um `organization_id` que **nenhuma resposta da API devolvia**, então eram inalcançáveis por qualquer coisa que não consultasse o Postgres à mão. `GET /api/v1/admin/organizations` é a rota de descoberta e a única de `admin.py` que responde **200 com lista vazia** em vez de 404 — ali não há recurso nomeado cuja existência se possa vazar —, e é a única que **não** chama `bind_admin_org`, porque a GUC de terceiro estágio guarda uma organização e a pergunta é *quais*. A tela é `/admin/organizacao`, sem `?project=`.
- Uma rota de demonstração na API teria de ramificar em `settings.demo_mode` — e desde a ADR 0033 **não há nenhuma**: a única existente nunca teve chamador e saiu, porque a regra da ADR 0029 ("o que ninguém consome é pergunta para a API") vale para a rota como vale para o campo. A casca de demonstração do produto vive no BFF, em `app/demo-overview.ts`. A new client endpoint takes `principal: CurrentPrincipal` — a `Depends`, not a header read — and ships with a negative-permission test (`test_authorization.py`). `POST /api/v1/agent-events` is the one exception and should stay the exception: it takes a key, not a principal.
- Adding a realm user means adding it to `SEED_USERS` in the same commit, with the same UUID — the consistency test is what keeps "authenticates but matches no row" from shipping.
- Every feature ships with an FDD (`docs/fdd/`) carrying acceptance criteria, telemetry, tests, and AI eval cases; prompt/retriever/model/tool changes require AI evals (`docs/ai/`).
