# CI Feedback and Automatic Repair

## Purpose

Define what happens after a task branch is pushed and a Pull Request triggers remote CI.

Local validation and remote CI are complementary controls:

```text
LOCAL VALIDATION
  catches defects early in the task worktree

REMOTE CI
  independently verifies the published revision in a clean/reproducible environment
```

Neither replaces the other.

A task MUST NOT be represented as `READY_FOR_HUMAN_REVIEW` while required remote CI is pending or failing.

## Lifecycle

```text
Builder
  ↓
local validation
  ↓
Reviewer
  ↓
commit + push + PR
  ↓
CI_PENDING
  ↓
remote CI result
  ├── green → CI_GREEN
  │             ↓
  │       READY_FOR_HUMAN_REVIEW
  │
  └── failed → CI_FAILED
                ↓
         classify failure
                ↓
        in task scope?
        ├── yes → CI_REPAIR_IN_PROGRESS
        │           ↓
        │        Builder fix
        │           ↓
        │        targeted local validation
        │           ↓
        │        Reviewer
        │           ↓
        │        commit + push
        │           ↓
        │        CI_PENDING ↺
        │
        └── no / ambiguous / infrastructure
                    ↓
             CI_REPAIR_BLOCKED
                    ↓
             HUMAN_ATTENTION_REQUIRED
```

## Required states

An EngineeringOS-compatible orchestration layer SHOULD distinguish at least:

```text
PR_OPEN
CI_PENDING
CI_FAILED
CI_REPAIR_IN_PROGRESS
CI_REPAIR_BLOCKED
CI_GREEN
READY_FOR_HUMAN_REVIEW
```

`READY_FOR_HUMAN_REVIEW` is a composite readiness state. It requires all applicable evidence, including `CI_GREEN`.

## Failure classification

Every failed required CI run MUST be classified before code is changed.

### CI_FAILURE_TASK_SCOPE

The failure is caused by the accepted task or by code/tests/configuration that the task is explicitly authorized to change.

Examples:

- a unit/integration test fails because of the task implementation;
- lint/typecheck/build fails in changed code;
- a browser/E2E test fails on behavior changed by the task;
- a migration/check generated by the task is invalid.

Default action: repair automatically within the existing task scope.

### CI_FAILURE_PREEXISTING

The same failure existed on the declared baseline or is demonstrably unrelated to the task revision.

Default action: record evidence. Do not silently expand task scope merely to make CI green. Project policy determines whether the PR can proceed with a known baseline failure.

### CI_FAILURE_INFRASTRUCTURE

The failure originates from CI infrastructure or required external configuration rather than task code.

Examples:

- runner outage;
- missing repository/organization secret not owned by the task;
- service outage;
- dependency registry/network failure;
- permission/configuration problem requiring operator action.

Default action: retry deterministically when policy permits; otherwise enter `CI_REPAIR_BLOCKED` and request operator attention. Do not change product code to mask infrastructure failure.

### CI_FAILURE_SCOPE_AMBIGUOUS

Evidence is insufficient to determine whether the failure belongs to the accepted task scope.

Default action: stop automatic repair and request a human decision or a scope clarification. Do not guess by broadening the task.

## Automatic repair authority

For `CI_FAILURE_TASK_SCOPE`, the harness/orchestrator MAY re-enter Builder execution without a new human gate when all of the following remain true:

- the original Task Contract is still valid;
- the repair stays within accepted scope;
- no new architecture/product/design decision is required;
- no human-only gate is crossed;
- the task worktree/branch remains the execution owner;
- the repair is reviewable and attributable to the failed CI evidence.

The Builder must not edit unrelated files just to obtain a green pipeline.

After a repair:

1. run the smallest sufficient local validation that covers the fix;
2. run any broader local validation required by project policy;
3. produce/update Builder evidence;
4. run a new Reviewer round for the changed revision;
5. commit and push;
6. wait for the new required CI result.

## Repair iteration guardrail

Automatic CI repair MUST be bounded.

Default:

```text
max_ci_repair_iterations = 3
```

Projects MAY configure another value, but it must be finite and known before execution.

`ci_repair_iterations` counts completed repair cycles after remote CI failures. It is distinct from `feedback_iterations` produced by normal Reviewer findings.

When the next failure would exceed the configured limit:

```text
CI_REPAIR_BLOCKED
HUMAN_ATTENTION_REQUIRED
```

The harness must publish the failure history and stop rather than looping indefinitely.

## CI observation and log retrieval

Waiting for CI, polling/checking status, listing failed jobs/steps, retrieving logs, extracting deterministic error context, and retrying an eligible failed job are orchestration operations and SHOULD NOT invoke an LLM by themselves.

Before giving CI evidence to a reasoning model, deterministic tooling SHOULD reduce logs to the minimum sufficient context, preserving provenance such as:

- workflow/run identifier;
- job and step;
- exit/result status;
- relevant error block;
- file/line when available;
- link/reference to full raw logs.

Do not send an entire large CI log to a model when a bounded error section is sufficient.

## Reviewer behavior during repair

A repair changes the revision under review. The previous Reviewer result does not automatically apply to the new commit.

The Reviewer evaluates the new revision using the relevant Task Contract, diff, Builder evidence, local validation, and the CI failure that motivated the repair.

The Reviewer MUST NOT return a final `REVIEW_PASS` as sufficient for human handoff while required remote CI for that published revision is still pending or failing. Code review can pass locally, but overall delivery readiness remains below `READY_FOR_HUMAN_REVIEW` until CI is green.

## Human review readiness

The harness may publish an open PR before CI finishes, but it MUST distinguish `PR_OPEN` from `READY_FOR_HUMAN_REVIEW`.

The final human-review gate requires, when applicable:

```text
Task Contract valid
+ local validation complete
+ Review Evidence Package complete
+ REVIEW_PASS / permitted review state
+ browser/runtime evidence complete
+ required remote CI = CI_GREEN
+ no blocking findings
= READY_FOR_HUMAN_REVIEW
```

A red or pending required CI run means the human may inspect the PR, but the harness must not claim the task is ready for merge.

## Relationship to deployment

`CI_GREEN` and human merge approval do not automatically authorize production deployment.

Deployment/staging/production gates remain project policy. A common progression is:

```text
PR + CI_GREEN
  ↓
Human review / optional preview or local acceptance
  ↓
Human merge
  ↓
Staging / deployment workflow
  ↓
Operational or client acceptance when applicable
```

## Evidence publication

The Issue/PR SHOULD make the CI lifecycle discoverable, including:

- current CI state;
- failed workflow/job reference;
- failure classification;
- `ci_repair_iterations`;
- repair commit(s);
- validations rerun;
- latest Reviewer result;
- final green run reference;
- remaining human gate.

Avoid noisy duplicate comments when a machine-owned status comment can be updated deterministically.

## FinOps

CI status checks, log retrieval, retry decisions based on deterministic error classes, evidence serialization, and polling do not require model tokens.

Model reasoning is appropriate only when interpretation is needed to diagnose or repair an in-scope engineering defect.

Useful future quality/cost metrics include:

- `ci_repair_iterations` per task;
- first-pass CI success rate;
- cost per accepted task;
- model/provider versus CI rework rate;
- time from PR open to `CI_GREEN`;
- human review burden.
