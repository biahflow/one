# T01 — Colunas de frescor/versão no Project e migração aditiva

A Task Contract é a unidade entregue a um executor, derivada de um plano válido. Um Builder não
cria a própria tarefa. É auto-contida: assuma o Core, este contrato e o repositório — nada mais.

## Goal

`Project` passa a ter as colunas do contrato de projeção versionado — `observed_at`,
`projection_version` e `synced_at` (fallback) — criadas por uma migração Alembic **aditiva** que
cita a ADR 0076 no corpo. Nenhuma leitura, projeção ou UI: só o schema e o modelo. Checável por
`alembic upgrade head` aplicar limpo e `test_migration_rules.py` passar.

## Scope

- `apps/api/src/portal_api/models/project.py` — acrescentar as três colunas ao modelo `Project`
  (nullable; `observed_at`/`synced_at` como `DateTime(timezone=True)`, `projection_version` inteiro).
- `apps/api/src/portal_api/db/migrations/versions/` — uma migração nova, aditiva, com `down_revision`
  apontando para o head atual, citando **ADR 0076** no docstring/corpo do arquivo.

## Out of Scope

- `sync_snapshot` consumir os campos (é T02) — não escrever valor nenhum ainda.
- `build_dashboard`/projeção (T04); qualquer schema Pydantic ou OpenAPI; qualquer UI.
- Tocar policy, RLS ou GRANT — esta tarefa é só coluna aditiva; se você sentir vontade de mexer em
  RLS, pare: não é desta tarefa.

## Acceptance Criteria

- `alembic upgrade head` aplica sem erro contra um Postgres com os papéis locais. Como se checa:
  `docker compose up -d postgres db-bootstrap` e então, de `apps/api/` com `DATABASE_MIGRATION_URL`
  no ambiente, `PYTHONPATH=src alembic upgrade head` retorna 0.
- Sem deriva entre modelo e migração: `PYTHONPATH=src alembic check` (de `apps/api/`) não acusa
  diferença.
- Migração aditiva e citando decisão: `PYTHONPATH=apps/api/src pytest apps/api/tests/test_migration_rules.py -q` passa (sem `drop`, e a
  ADR 0076 citada no corpo satisfaz a regra 4 caso o AST detecte gatilho estrutural — aqui não há,
  mas a citação evita ambiguidade).
- Suíte de dados não regride: `PYTHONPATH=apps/api/src pytest apps/api/tests -q` verde (auto-pula os
  testes de integração se não houver Postgres).

## Context to Read First

- `docs/adr/0076-o-snapshot-que-precisava-de-versao-e-hora.md` — o contrato (o que cada coluna
  significa; `observed_at` da origem vs `synced_at` fallback rotulado).
- `apps/api/src/portal_api/models/project.py` — o modelo `Project` e as colunas existentes
  (`archived_at`, `source_deleted_at`) como precedente de coluna nullable de timestamp.
- Uma migração recente em `apps/api/src/portal_api/db/migrations/versions/` (ex.: `0003_journey_and_roi`,
  `0004_project_health`) como molde de migração aditiva de coluna.
- `CLAUDE.md` (seção de migrações; `search_path` não-qualificado) e `AGENTS.md` (regra 4).

## Known Risks

- Esquecer o `down_revision` correto quebra a cadeia linear do Alembic — confira o head atual antes.
- Qualificar a tabela no schema (o repositório fixa `search_path` para `portal,public`; modelos são
  **não-qualificados**). Qualificar geraria falsa deriva no `alembic check`.
- `projection_version` deve ser nullable nesta fatia (linhas existentes não têm versão); NOT NULL
  quebraria o upgrade sobre dados existentes.

## Human Gates

- Merge da branch da tarefa é gate humano — não faça merge, não habilite auto-merge.
- A migração é aditiva por contrato (ADR 0066); se algo empurrar para um `drop`/`alter` destrutivo,
  pare e reporte `Human decisions required` — não contorne o `test_migration_rules.py`.
